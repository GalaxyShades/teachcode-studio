# Lesson content API

Studio authors, publishes, and serves content. The student app owns student accounts, enrolment, attempts, scores, completion rules, and learning progress. Reading content never records a completion or changes student state.

**Base path:** `/api/v1/content`. These endpoints are public and read-only; no login, cookie, API key, or shared database schema is needed.

- [OpenAPI specification](content-api.openapi.json): import into an API client or use for client generation.
- [Complete chapter example](examples/published-chapter.json): copyable JSON, validated against the response schema.
- [Response schemas](../lib/public-contract.ts): the code used to validate and allowlist API responses.
- [Authoring API](api.md): staff authentication, drafts, publishing, and version history.

## Discover and fetch content

| Method | Endpoint                                                  | Response                                                      |
| ------ | --------------------------------------------------------- | ------------------------------------------------------------- |
| GET    | `/api/v1/content/courses`                                 | Array of `{id, slug, title, description}`                     |
| GET    | `/api/v1/content/courses/{courseId}`                      | Course details, ordered `lessons`, and `unassignedChapters`   |
| GET    | `/api/v1/content/courses/{courseId}/chapters/{chapterId}` | Current published chapter, including ordered steps and blocks |

Each lesson in an outline has `{id, title, chapters}`. Each chapter summary has `{id, lessonId, slug, title, description, revisionId, contentUrl}`. `lessonId` is null for an unassigned chapter. Follow `contentUrl` relative to the **Studio origin**, not the student app origin.

```bash
STUDIO_URL=http://localhost:3000
curl --fail-with-body "$STUDIO_URL/api/v1/content/courses"
# Copy a course id from the response, then a chapter's contentUrl from its outline.
COURSE_ID=a1000000-0000-4000-8000-000000000001
curl --fail-with-body "$STUDIO_URL/api/v1/content/courses/$COURSE_ID"
CHAPTER_ID=a1000000-0000-4000-8000-000000000002
curl --fail-with-body "$STUDIO_URL/api/v1/content/courses/$COURSE_ID/chapters/$CHAPTER_ID"
```

The UUIDs above are examples; use IDs returned by your running Studio. Titles and URL slugs are not accepted as path IDs. UUIDs are generated by Studio, not by the AI writing chapter Markdown. Step and block IDs can be descriptive strings such as `first-program` and `hello-example`.

An empty catalogue returns `200 []`. Courses without published chapters, drafts, archived chapters, unpublished courses, and chapters belonging to a different course return 404 when requested individually. Empty lesson groups are omitted. Array order is presentation order; no client sorting is needed. There is no pagination or filtering in v1.

## Chapter response

| Field                          | Meaning                                                  |
| ------------------------------ | -------------------------------------------------------- |
| `apiVersion`                   | Content contract major version, currently `1`            |
| `courseId`, `chapterId`        | Stable Studio resource identifiers                       |
| `revisionId`                   | Identifier of the immutable published snapshot returned  |
| `title`, `slug`, `description` | Published chapter metadata                               |
| `track`                        | `Python`, `R`, or `literacy`                             |
| `level`                        | `year 1`, `year 2`, or `advanced`                        |
| `mode`                         | `lesson`, `exercise`, or `quiz`                          |
| `programmingLanguage`          | `Python`, `R`, or an empty string                        |
| `tags`                         | Array of labels                                          |
| `presentation`                 | Presentation hint, such as `guided`; an open string      |
| `runtimeScope`                 | `per-step` or `lesson-wide`; intended code-runtime scope |
| `steps`                        | Nonempty ordered array of `{id, title, blocks}`          |

Every block includes `id`, `type`, `visible: true`, and an optional `advanced` flag. A step can have no public blocks after private cards are removed. `advanced` is a display hint, not access control.

| Block `type`      | Content fields (optional fields marked `?`)                                |
| ----------------- | -------------------------------------------------------------------------- |
| `text`            | `markdown`                                                                 |
| `task`            | `statement`, `context`, `functions: [{name, summary}]`                     |
| `quick-reference` | `title`, `markdown`                                                        |
| `worked-example`  | `title?`, `language`, `code`, `explanation`, `runnable`, `expectedOutput?` |
| `figure`          | `imageUrl`, `alt`, `caption?`, `markdown`                                  |
| `mcq`             | `question`, `multiple`, `choices: [{id, text, correct}]`, `explanation`    |
| `code-exercise`   | `language`, `starterCode`, `execution`, `prompt`, `expectedOutput?`        |
| `reflection`      | `prompt`                                                                   |
| `data-asset`      | `url`, `filename`, `runtimePath?`, `description`                           |

Code block `language` is `python` or `r`. `execution` is `browser` or `server`, but Studio provides **no server execution endpoint**. A consuming app must explicitly support the requested runtime or show an unavailable state. New worked examples default to runnable in the authoring UI; clients should honor the returned boolean.

The API omits draft versions, source Markdown, invisible cards, tutor configuration, code-review cards, exercise solutions/check scripts, style/randomisation/review configuration, and reflection rubrics. Public fields are explicitly allowlisted, including nested fields. **MCQ correct answers and explanations are public** for immediate feedback; this API is not a secure grading service.

## Fetch from the student app

```ts
async function fetchChapter(studioOrigin: string, contentUrl: string) {
  const response = await fetch(new URL(contentUrl, studioOrigin), {
    credentials: "omit",
    cache: "no-store",
    signal: AbortSignal.timeout(10_000),
  });
  if (!response.ok) {
    // A reverse proxy may return non-JSON errors.
    const error = await response.json().catch(() => null);
    throw new Error(
      `${response.status}: ${error?.code ?? "CONTENT_FETCH_FAILED"}`,
    );
  }
  const chapter = await response.json();
  if (chapter.apiVersion !== 1)
    throw new Error("Unsupported content API version");
  return chapter; // Validate with a generated client/schema before rendering.
}
```

Configure `ALLOWED_CORS_ORIGINS=https://learn.example.com,http://localhost:3001` on Studio for browser requests from those exact origins. Restart after changing environment configuration. CORS does not gate public access; server-to-server clients can fetch without it. No credentialed cross-origin requests are needed.

GET success and handled errors include `Cache-Control: no-store`, `Vary: Origin`, and `X-Content-API-Version: 1`. Allowed browsers can read the version header. OPTIONS returns 204; GET endpoints also support framework-provided HEAD. Unsupported methods return the framework's 405 response, which is not covered by the JSON error contract below.

## Errors and retries

Handled API errors use `{ "error": "Readable message", "code": "MACHINE_CODE" }`.

| Status | Code                          | Client action                                              |
| ------ | ----------------------------- | ---------------------------------------------------------- |
| 400    | `INVALID_ID`                  | Fix malformed UUID path parameters; do not retry unchanged |
| 404    | `PUBLISHED_CONTENT_NOT_FOUND` | Show content unavailable and refresh the course outline    |
| 500    | `INTERNAL_ERROR`              | Offer retry; internal database details are withheld        |

Network timeouts and transient 5xx responses can be retried a small number of times with increasing delays and jitter. Never retry indefinitely. Hosting proxies can return other statuses or non-JSON bodies. There is no application-level rate limiter in v1; configure operational limits at the deployment layer as traffic grows.

## Publication consistency and progress keys

- Each chapter response reads one consistent database snapshot, even during republishing or revision pruning. Each outline also uses one coherent snapshot. SQLite serializes access; PostgreSQL uses a read-only repeatable-read transaction.
- Separate requests can observe different publications. If an outline lists revision A and fetching its content returns revision B, use the **returned chapter's** revision ID for the content actually shown. Refetch the outline if alignment matters.
- Draft changes remain private until deliberate publication. Chapter metadata and blocks come from the selected publication. Course names, lesson names, assignments to lessons, and outline order reflect the live course structure.
- Store progress in the student app keyed by its student ID and Studio `chapterId`; include `stepId`/block `id` where needed and `revisionId` for each attempt. Scope step/card identifiers to the chapter: they are not globally unique. Preserve IDs when editing the same logical content. The student app decides what republishing or deletion means for completion.
- Studio retains up to five published snapshots for staff restore controls. The public API serves **only the current publication**, with no historical revision lookup. Keep any assessment evidence required for long-term auditing in the student app.
- Fetch again when opening content. `no-store` prevents compliant caches from retaining responses; it cannot revoke a document already downloaded or currently displayed.

## Contract ownership and evolution

The versioned public API is the integration boundary: the student app should not import Studio's database schema or query its tables. Authoring endpoints remain internal to Studio and use the existing database-oriented names (`modules`/`lessons`); they are not the student content contract.

The new public API starts at `/api/v1/content` with course → lesson → chapter terminology. There are no legacy public-route aliases. `apiVersion` and `X-Content-API-Version` identify the content contract; `revisionId` identifies published content, not an API version. OpenAPI's `info.version` identifies the specification release.

Future incompatible changes should use a new major API path. Additive changes should be documented before deployment. Consumers should ignore unfamiliar metadata fields and show an explicit unsupported-card state for unknown block kinds rather than marking them complete. This is an evolution policy, not a promise that clients never need updates.

Regenerate the specification and example after changing the public schemas:

```bash
npm run docs:api
npm test
```

Tests validate the example, check that the specification matches the schemas, exercise error handling and private-field removal, and cover publication/unpublication with SQLite and PostgreSQL.

When rendering, treat Markdown and asset URLs as authored input: sanitize rendered content, avoid raw HTML execution, and only execute code within an appropriate isolated runtime. Studio doesn't persist student progress or provide enrolment authorization through these endpoints.
